A storefront needs the identity of the shop on every page (its name, logo and contact details), the legal pages for the footer and the checkout, and the regions it sells to. The region matters most: the zone of a request decides the currency of every price the catalog and the cart return.

These endpoints are public and read-only. They answer `GET` requests without a customer token, and the responses follow the [JSON:API conventions](/3.x/store-api/json-api), except where this page says otherwise.

## Endpoints

All these routes sit in the public route group. A show endpoint answers `404` with the code `not_found` for a record that does not exist or that the merchant disabled.

## Reading the Store Settings

The header, the footer and the contact page show the shop name, the logo, the address and the social links.

<Endpoint id="get-store-settings" method="GET" path="/store/settings" auth="public">

<Params title="Query parameters">

<Field name="fields[settings]" type="string">
  Comma-separated attributes to keep, as described in [Sparse fieldsets](/3.x/store-api/json-api#sparse-fieldsets).
</Field>

</Params>

`/store/settings` returns them in one call, along with the default currency and the languages of the shop:

```bash title="Request"
curl http://localhost:8000/store/settings \
  -H "Accept: application/vnd.api+json"
```

### Caching the Settings

A storefront reads the settings on nearly every page render, so the response is built to be cached by the browser, a CDN or your own server. It is public, with `max-age` and `s-maxage` set to `settings.max_age` in `config/shopper/api.php` (300 seconds by default), and it carries an `ETag` and `Vary: Accept-Language`.

To revalidate a cached copy, send its ETag back in `If-None-Match`:

```bash title="Request"
curl -i http://localhost:8000/store/settings \
  -H "Accept: application/vnd.api+json" \
  -H 'If-None-Match: "5d41c7a2e9b04f1d8c3e6a7b2f9d0e14"'
```

While nothing changed, the API answers `304 Not Modified` with an empty body, and the storefront keeps its copy. A change the merchant makes in the admin panel reaches visitors at most `max_age` seconds later, once every cache has expired its copy.

### Language

The `Accept-Language` header picks the language of the response among the `supported_locales`, which come from `locales` in `config/shopper/admin.php`. A language the shop does not support falls back to the first locale of that list, and a request without the header gets the default locale of the Laravel app. `default_locale` tells the storefront which language it got.

The language changes the country names: `country.name` in the settings, and `translated_name` on [countries](#countries). A storefront that shows a language switcher sends the visitor's choice in `Accept-Language` on every request.

## Legal Pages

The footer links to the refund, privacy, terms and shipping policies, and the checkout often asks the customer to accept the terms. Shopper creates four pages at install, with the slugs `refund`, `privacy`, `terms` and `shipping`, and the merchant writes their content in the admin panel. The API returns the enabled ones only.

</Field>

<Field name="sort" type="string">

</Field>

<Field name="page[size]" type="integer" default="15">

</Field>

<Field name="page[number]" type="integer" default="1">
  The page to return, from 1 to 100.
</Field>

<Field name="page[cursor]" type="string">
  Switches to cursor pagination. An empty value returns the first page.
</Field>

<Field name="fields[legals]" type="string">
  Comma-separated attributes to keep, as described in [Sparse fieldsets](/3.x/store-api/json-api#sparse-fieldsets).

`/store/legals` lists them, for the footer links. It accepts `filter[title]` (partial match), `sort=title` or `sort=updated_at`, and the [pagination](/3.x/store-api/json-api#pagination) parameters.

```bash title="Request"
curl -g "http://localhost:8000/store/legals?fields[legals]=title,slug" \
  -H "Accept: application/vnd.api+json"
```

```json title="Response 200"
{
    "data": {
```

## Countries

Address forms need a country list, and a storefront that guesses the visitor's region needs to know which zone a country belongs to. `/store/countries` returns every country of the world, about 250, whether or not the shop sells there. For the countries the shop sells to, read the countries of its [zones](#zones) instead.

<Endpoint id="get-store-countries" method="GET" path="/store/countries" auth="public">

The listing is paginated, 15 countries per page by default and 100 at most. It accepts these parameters:

<Params title="Query parameters">

<Field name="filter[name]" type="string">
  Countries whose English name contains the value.
</Field>

<Field name="filter[cca2]" type="string">
  Exact ISO 3166-1 alpha-2 code, such as `FR` or `US`.
</Field>

<Field name="filter[cca3]" type="string">
  Exact ISO 3166-1 alpha-3 code, such as `FRA` or `USA`.
</Field>

<Field name="filter[region]" type="string">
  Exact region, such as `Europe` or `Americas`.
</Field>

<Field name="filter[zone]" type="string">
  Code of a zone the country belongs to, such as `EU`. Disabled zones match too.
</Field>

<Field name="sort" type="string">
  `name`. Prefix with `-` for descending order.
</Field>

<Field name="include" type="string">
  `zones`: the enabled zones the country belongs to.
</Field>

<Field name="page[size]" type="integer" default="15">
  Countries per page, from 1 to 100.
</Field>

<Field name="page[number]" type="integer" default="1">
  The page to return, from 1 to 100.
</Field>

<Field name="page[cursor]" type="string">
  Switches to cursor pagination. An empty value returns the first page.
</Field>

<Field name="fields[countries]" type="string">
  Comma-separated attributes to keep, as described in [Sparse fieldsets](/3.x/store-api/json-api#sparse-fieldsets).
</Field>

<Field name="fields[zones]" type="string">
  Attributes to keep on the included zones.
</Field>

</Params>

This request lists the countries of Europe by name:

```bash title="Request"
curl -g "http://localhost:8000/store/countries?filter[region]=Europe&sort=name" \
  -H "Accept: application/vnd.api+json"
```

</Endpoint>

</Field>

<Params title="Query parameters">

<Field name="include" type="string">

To read one country, pass its two-letter or three-letter ISO code in any case. This request reads the United States with its zones, in French:


| Status | Code | When |

A country carries `name` (the common English name), `translated_name` (the name in the language of the request, or the English name when no translation exists), `name_official`, `region`, `subregion`, `cca2`, `flag` (the URL of an SVG flag served by your app), `latitude` and `longitude`. The three-letter code works in the path and in `filter[cca3]`, but the resource does not return it.

## Zones

A zone is a region of the shop, such as "Europe" or "United States", with its own currency, carriers and payment methods. A storefront sends the code of the visitor's zone in the `X-Shopper-Zone` header, and the API prices the catalog and the cart for that zone. The [Zones](/3.x/zones#what-the-zone-changes) page lists everything a zone changes.

## Currencies

A currency switcher needs the codes the shop sells in, and a price label needs the symbol of the currency. The codes come from `currencies` in the [settings](#reading-the-store-settings). `/store/currencies` returns every enabled currency, and Shopper enables all 158 currencies at install, so the listing holds far more codes than the shop sells in.

<Endpoint id="get-store-currencies" method="GET" path="/store/currencies" auth="public">

<Params title="Query parameters">

</Field>

<Field name="filter[code]" type="string">

## Picking a Zone and a Currency

The API never guesses where a visitor is. The storefront decides the zone, sends it with every request, and the API prices everything for it. A typical flow on the first visit:

<Steps>

<Step title="Read the store settings">

Call `/store/settings` once and cache it. `default_currency` is the currency of a visitor outside every zone, and `currencies` lists the codes for a currency switcher.

</Step>

<Step title="Load the zones and their countries">

Call `/store/zones?include=countries` and keep a map from each country code (`cca2`) to its zone `code`. Add `page[size]=100` when the shop has more than 15 zones. Zones change rarely, so cache the map with the settings.

</Step>

<Step title="Find the visitor's country">

Take the country from your CDN or hosting provider's geolocation header, from a country selector, or from the shipping address of a returning customer. Look it up in the map. A country outside every zone gets no zone, and a cart without a zone answers `422` when it asks for shipping options, so send the default zone or tell the visitor the shop does not deliver to their country.

</Step>

<Step title="Send the zone with every request">

Send the zone code in `X-Shopper-Zone` on every catalog and cart request, and store it in a cookie so the next visit skips the lookup:

```bash title="Request"
curl http://localhost:8000/store/products \
  -H "Accept: application/vnd.api+json" \
  -H "X-Shopper-Zone: US"
```

Prices then come in the zone currency, and `meta.currency` confirms it: `USD` for this request. Every response lists `X-Shopper-Zone` in `Vary`, so a shared cache keeps one copy per zone.

</Step>

<Step title="Let the visitor switch currency">

To show prices in another currency of the shop without changing the zone, add `filter[currency]` to the catalog requests, as described in [Prices, currency and stock](/3.x/store-api/catalog). The cart takes its own currency, set when it is created or updated: see [Cart](/3.x/store-api/cart).

</Step>

</Steps>

The API does not reject a zone code it cannot find. An unknown or disabled code falls back to the default zone, whose code is set in `SHOPPER_API_DEFAULT_ZONE`, or to no zone at all when that variable is empty, and prices then come in the default currency of the shop. A typo in the header therefore shows the wrong currency instead of an error: compare `meta.currency` with the currency you expect while you build the storefront.

The API caches each zone it resolves, with its currency, for 60 seconds (`zone.cache_ttl` in `config/shopper/http.php`), and clears that cache when the zone is saved or deleted. A change to the currency itself, such as disabling it, can take up to a minute to reach the API. A cart created with `X-Shopper-Zone` keeps that zone and takes its currency, unless the request sets another `currency_code`.

The sales channel works the same way through the `X-Shopper-Channel` header, and decides which products the catalog returns. See [Request headers](/3.x/store-api#request-headers) and the [Channels](/3.x/channels#the-store-api) page. The [Zones](/3.x/zones#resolving-a-zone) page covers the resolution order and the `zone` settings of `config/shopper/http.php`, including the `resolver` class you can replace with your own.
