Once the checkout places an order, the storefront shows it at three moments: on the confirmation page right after payment, in the order history of the account, and on a tracking page while the parcel travels. A digital product adds a fourth: the download of the files the customer paid for. This guide follows those moments in order.

Orders are read-only in the Store API. The storefront never changes an order: the merchant updates it in the admin panel, and payment and carrier webhooks move its statuses. The [Orders](/3.x/orders) page covers the order model and its life cycle.

## Endpoints

The confirmation lookup and the shipment tracking sit in the public route group and work without a token. The account endpoints need the bearer token of a signed-in customer, described in [Logging in](/3.x/store-api/authentication#logging-in).

| Method | Path | Purpose | Customer token |
|--------|------|---------|----------------|
| `GET` | `/store/orders/{orderId}` | Order confirmation | No |
| `GET` | `/store/customers/me/orders` | Order history | Yes |
| `GET` | `/store/customers/me/orders/{orderId}` | Order details | Yes |
| `GET` | `/store/shipments/{shipmentId}` | Shipment tracking | No |
| `GET` | `/store/customers/me/orders/{orderId}/items/{itemId}/files/{fileId}` | Download link of a purchased file | Yes |
| `GET` | `/store/files/{fileId}` | The file itself, through a signed link | No, the signature grants access |

## Order Confirmation

The confirmation page thanks the customer and recaps what they bought, for guests and customers alike. The checkout returns the ID of the new order, as the [Checkout](/3.x/store-api/checkout) guide shows, and the storefront reads the order with it. This order belongs to a signed-in customer, so the request carries their token, as [Who Can Read an Order](#who-can-read-an-order) explains:

```bash title="Request"
curl "http://localhost:8000/store/orders/01JQ8Z6N4W2T5V3K9R7M1H0XAB?include=items" \
  -H "Accept: application/vnd.api+json" \
  -H "Authorization: Bearer 1|customer-token"
```

The API answers `200 OK` with the order and its lines in `included`:

### Who Can Read an Order

The confirmation lookup needs no token, so a guest can see the order they just placed. Access follows from who placed the order:

| Order placed | Who can read it here |
|--------------|----------------------|
| As a guest, without a token | Anyone holding the order ID |
| By a signed-in customer | Only requests with that customer's token |

The order ID is a ULID, 26 characters with 80 random bits, so it cannot be guessed, but for a guest order it works like a password. Keep it in the confirmation URL or the session of the visitor, and out of logs and analytics events.

A customer order read without the token, or with the token of another customer, answers `404 not_found`, the same answer as an ID that does not exist, so the API never confirms that an order exists.

Because a guest order is readable by its ID alone, this endpoint returns less than the account endpoints:

- `items` is the only relationship you can include. Addresses, the payment method, shipments and refunds are on the [Order details](#order-details) endpoint, for signed-in customers.
- The items carry no `files`, even for a paid order: downloads go through the account, as [Downloading purchased files](#downloading-purchased-files) describes.

Any other include answers `422` with the `include_not_allowed` code:

```json title="Response"
{
    "errors": [
        {
            "status": "422",
            "code": "include_not_allowed",
            "title": "Unprocessable Content",
            "detail": "Only `items` can be included on the order confirmation lookup. Use the account order endpoint for the full order.",
            "source": {
                "pointer": "/data/attributes/include"
            }
        }
    ]
}
```

The account endpoints answer an include outside their list with `400 bad_request` instead, so handle both codes if your storefront builds include lists dynamically.

## The Order Resource

The confirmation, the history and the details all return the same `orders` resource. Its attributes summarize the order; the lines, addresses and shipments come through includes.

| Attribute | Type | Description |
|-----------|------|-------------|
| `number` | string | The number the customer sees, such as `ORD-20261117-000042`. The format is set in the shop configuration, as [Orders](/3.x/orders#order-number-generation) describes. |
| `status` | string | Where the order stands for the merchant. |
| `payment_status` | string | Where the payment stands. |
| `shipping_status` | string | Where the delivery stands, across every package. |
| `total` | integer | Sum of the lines in cents, after line discounts, without shipping. |
| `tax_amount` | integer | Tax of the order in cents. |
| `shipping_amount` | integer | Shipping cost in cents. |
| `price_amount` | integer | What the customer paid, in cents. |
| `currency_code` | string | ISO code of the order currency, such as `EUR`. |
| `email` | string or null | Email the order was placed with. |
| `created_at` | string | When the order was placed, ISO 8601. |

### Amounts

Every amount is an integer in cents: `14390` is €143.90. The [Money](/3.x/money) page covers cents and formatting.

Show `price_amount` as the amount paid. It is the sum of the lines, minus discounts, plus shipping, plus taxes when prices exclude tax. `total` covers the lines only, so it fits a "Subtotal" row, not the amount charged. In the example above, the lines sum to €138.00, shipping adds €5.90, and the customer paid €143.90, of which €23.98 is VAT included in the prices. The [Orders](/3.x/orders#order-total) page details how the totals are computed.

### Statuses

An order carries three statuses, each moved by a different part of the shop. The [Orders](/3.x/orders#order-status) page describes each value and when it changes.

| Attribute | Values |
|-----------|--------|
| `status` | `new`, `processing`, `completed`, `cancelled`, `archived` |
| `payment_status` | `pending`, `authorized`, `paid`, `partially_refunded`, `refunded`, `voided` |
| `shipping_status` | `unfulfilled`, `partially_shipped`, `shipped`, `partially_delivered`, `delivered`, `partially_returned`, `returned` |

### Relationships

These relationships appear when you include them. On the confirmation lookup, only `items` is available.

| Relationship | Type | Attributes |
|--------------|------|------------|
| `items` | `order-items` | `name`, `sku`, `quantity`, `unit_price_amount`, `total` (unit price times quantity, minus the line discount), `metadata`, and `files` for a downloadable product on the order details |
| `shippingAddress`, `billingAddress` | `order-addresses` | `first_name`, `last_name`, `full_name`, `company`, `street_address`, `street_address_plus`, `city`, `state`, `postal_code`, `phone`, `country_name` |
| `paymentMethod` | `payment-methods` | `title`, `slug`, `description`, `instructions`, `driver`, `logo` |
| `shippings` | `order-shippings` | The packages of the order, as [Tracking a shipment](#tracking-a-shipment) describes |
| `refund` | `order-refunds` | `status`, `amount` in cents, `currency`, `reason`, `created_at` |

The order keeps a copy of the addresses and of each line as they were at checkout, so later changes to the customer's saved addresses or to the catalog do not alter a past order.

### Filters, Sorting and Includes

The list accepts these query parameters, described in [JSON:API Conventions](/3.x/store-api/json-api):

| Parameter | Values | Description |
|-----------|--------|-------------|
| `filter[status]` | One order status, such as `processing` | Keeps the orders in that status. See [Filters](/3.x/store-api/json-api#filters). |
| `sort` | `created_at`, `-created_at` | Oldest or newest first. The default is `-created_at`. See [Sorting](/3.x/store-api/json-api#sorting). |
| `include` | `items`, `shippingAddress`, `billingAddress`, `paymentMethod`, `shippings`, `shippings.events`, `refund` | Relationships to add, comma-separated. See [Includes](/3.x/store-api/json-api#includes). |
| `page[size]` | 1 to 100 | Orders per page. The default is 15. |
| `page[number]` | 1 to 100 | Page to return. |
| `page[cursor]` | The cursor of a previous page | Switches to cursor pagination. See [Pagination](/3.x/store-api/json-api#pagination). |

For a tab that shows the orders still on their way:

```bash title="Request"
curl -g "http://localhost:8000/store/customers/me/orders?filter[status]=processing&page[size]=10" \
  -H "Accept: application/vnd.api+json" \
  -H "Authorization: Bearer 1|customer-token"
```

## Tracking a Shipment

A tracking page shows where a package is, without asking the customer to sign in, so it works from a link in a shipping email. An order can ship in several packages; each one is a shipment with its own ID, carrier and tracking number.

The storefront gets the shipment ID from `include=shippings` on the [order details](#order-details), where each `order-shippings` resource is one package. A guest has no account to read, so pass the ID in the email you send when the package ships: the `shipment.*` webhooks carry it as the `id` of the package, as [Webhooks](/3.x/webhooks#shipment-data) describes.

```bash title="Request"
curl "http://localhost:8000/store/shipments/01JQ9B2C4D6E8F0G1H3J5K7M9N?include=events" \
  -H "Accept: application/vnd.api+json"
```

The API answers `200 OK` with the shipment and its tracking events, oldest first:

## Downloading Purchased Files

A customer who buys a digital product, such as a PDF guide or a font pack, downloads its files from their account. The files sit on a private disk with no public URL, so the storefront asks the API for a short-lived link each time the customer clicks **Download**.

<Steps>
<Step title="Read the order with its items">

Request the [order details](#order-details) with `include=items`. Once the payment status of the order is `paid` or `partially_refunded`, each item of a downloadable product carries `files`, with the `id`, `name`, `extension` and `size` in bytes of each file. Show one **Download** button per file.

</Step>
<Step title="Ask for a link when the customer clicks">

Call the file endpoint with the order ID, the item ID and the file `id`:

```bash title="Request"
curl http://localhost:8000/store/customers/me/orders/01JQ8Z6N4W2T5V3K9R7M1H0XAB/items/01JQ8Z6N5C8E2D4F6G1J3K5M7P/files/4b1f0c2e-8d6a-4f3e-9a51-6c2d7e9b0a13 \
  -H "Accept: application/vnd.api+json" \
  -H "Authorization: Bearer 1|customer-token"
```

</Step>
<Step title="Send the browser to the link">

Redirect the browser, or open a new tab, to the `url` of the response right away. The file comes back as an attachment named after the file, such as `sneaker-care-guide.pdf`.

</Step>
</Steps>

The API answers `200 OK` with the link and the moment it expires. This response is a plain `data` object, not a JSON:API resource:

```json title="Response"
{
    "data": {
        "url": "http://localhost:8000/store/files/4b1f0c2e-8d6a-4f3e-9a51-6c2d7e9b0a13?expires=1794995232&signature=b7e3c1f0a9d24e6b8c5f1a7d3e9b2c4f6a8d0e2b4c6f8a1d3e5b7c9f0a2d4e6b",
        "expires_at": "2026-11-18T09:47:12+00:00"
    }
}
```

The link works for five minutes. Ask for a new one at every click rather than storing it, and never put it in an email: anyone holding the link downloads the file until it expires. The API keeps no count of links or downloads per customer: only the general [rate limit](/3.x/store-api#rate-limits) of the Store API applies.

The shape of the link depends on the disk that holds the files, the `shopper.media.storage.files_disk` setting described in [Products](/3.x/products#downloadable-files):

- On an S3 disk, the link is a temporary URL of the bucket, and the download goes straight to S3.
- On any other disk, such as the default `local` disk, the link points to `GET /store/files/{fileId}`, a route signed by your app, which streams the file. A link that was altered or has expired answers `403`.

| Status | Code | When |
|--------|------|------|
| `401` | `unauthenticated` | The request has no valid customer token. |
| `403` | `forbidden` | The order is not paid yet: "The files of this order are available once it is paid." |
| `404` | `not_found` | The order is not one of the customer's, the item is not in the order, or the file does not belong to the product of the item. |

Downloads go through the account only. A guest order has no file endpoint, so a store that sells digital products asks buyers to create an account, or sends the files another way.

When the files move to another disk with the `shopper:files:secure` command, each file gets a new `id`. Read the order again rather than reusing a file `id` stored earlier.
