title: Authentication
description: Register and log in customers, send their bearer token, reset passwords, and know what a guest can do without a token.
---

Most of the Store API answers without any credentials, so a visitor can browse the catalog, fill a cart and check out as a guest. A customer account adds a profile, saved addresses, an order history and carts that follow the customer from one device to another. The API identifies a customer with a bearer token issued by [Laravel Sanctum](https://laravel.com/docs/sanctum) at registration and login.

This page follows the life of that token: register or log in to get one, send it on each request, then log out or reset the password.

## Endpoints

The authentication endpoints sit under `/store/auth`. All of them except logout are public and share the `shopper-api-auth` rate limit of 20 requests per minute per IP address, described in [Rate Limits](/3.x/store-api#rate-limits).

<Routes>
  <Route method="POST" path="/store/auth/register" href="#post-store-auth-register">Create a customer account and return a token</Route>
  <Route method="POST" path="/store/auth/login" href="#post-store-auth-login">Check the email and password and return a token</Route>
  <Route method="POST" path="/store/auth/logout" href="#post-store-auth-logout">Revoke the token sent with the request</Route>
  <Route method="POST" path="/store/auth/forgot-password" href="#post-store-auth-forgot-password">Email a password reset link</Route>
  <Route method="POST" path="/store/auth/reset-password" href="#post-store-auth-reset-password">Set a new password from the reset link</Route>
</Routes>

The request bodies are flat JSON objects sent with `Content-Type: application/json`, as on every Store API route.

## Guest and Customer Requests

A request without an `Authorization` header is a guest request. A guest can call every public route: the catalog, the store settings, the regions, the cart and its checkout, and the order confirmation lookup. A guest checkout only needs an email on the cart, as the [Checkout](/3.x/store-api/checkout) guide shows.

A request with a valid customer token runs as that customer. The token gives access to:

- the routes under `/store/customers/me`: profile, avatar, addresses, order history and digital downloads, covered in the [Customers](/3.x/store-api/customers) and [Orders](/3.x/store-api/orders) guides;
- `POST /store/carts/{cartId}/transfer`, which attaches a guest cart to the customer;
- the carts that belong to the customer. A cart attached to a customer answers `404 Not Found` to any request that does not carry that customer's token, so a cart ID alone never exposes a customer's cart;
- prices calculated for the customer. The API passes the customer to the price resolver, which ignores it by default; a custom resolver can return customer group prices, as described on the [Pricing](/3.x/pricing) page.

The same public route can answer differently for a guest and for a customer, which is why product responses that include calculated prices carry `Vary: Authorization`.

## Registering a Customer

Registration creates the account and logs the customer in at once: the response carries the token, so the storefront does not need a second call to log in. Send the guest cart ID in `cart_id` to keep the products the visitor added before signing up.

<Endpoint id="post-store-auth-register" method="POST" path="/store/auth/register" auth="public" limit="auth">

<Params title="Query parameters">

<Field name="fields[customers]" type="string">
  Comma-separated attributes to return, such as `first_name,last_name`. See [Sparse fieldsets](/3.x/store-api/json-api#sparse-fieldsets).
</Field>

</Params>

<Params title="Body">

<Field name="last_name" type="string" required>
  The last name of the customer, up to 255 characters.
</Field>

<Field name="first_name" type="string">
  The first name of the customer, up to 255 characters.
</Field>

<Field name="email" type="string" required>
  A valid email address, up to 255 characters, not used by another account.
</Field>

<Field name="password" type="string" required>
  The password. It follows the application's `Password::defaults()` rule: at least 8 characters unless your application sets other defaults.
</Field>

<Field name="opt_in" type="boolean" default="false">
  Whether the customer accepts marketing emails.
</Field>

<Field name="cart_id" type="string">
  The ID of a guest cart to attach to the new account.
</Field>

</Params>

This request creates the account of Camille Martin and attaches her guest cart:

```bash title="Request"
curl -X POST "http://localhost:8000/store/auth/register" \
  -H "Accept: application/vnd.api+json" \
  -H "Content-Type: application/json" \
  -d '{
    "first_name": "Camille",
    "last_name": "Martin",
    "email": "camille.martin@example.com",
    "password": "sneakers-in-paris",
    "opt_in": true,
    "cart_id": "01JD8Z6Q4M3K2V7R9T5W1XNB0C"
  }'
```

The API answers `201 Created` with the customer and, in `meta`, the token and the ID of the customer's cart:

```json title="Response 201"
{
    "data": {
        "id": "01JD9B2K7X4N8R3T6V1Y5Z0QWE",
        "type": "customers",
        "attributes": {
            "first_name": "Camille",
            "last_name": "Martin",
            "email": "camille.martin@example.com",
            "avatar": "https://ui-avatars.com/api/?name=Camille+Martin&color=1d4ed8&background=dbeafe",
            "avatar_type": null,
            "phone_number": null,
            "gender": null,
            "birth_date": null,
            "opt_in": true,
            "email_verified": false,
            "email_verified_at": null,
            "created_at": "2026-11-19T10:24:31+00:00"
        }
    },
    "meta": {
        "token": "3|Xk9mWqT2xLp8RzN6vHc1YbJ7sDe5GaU0iOk3nQw49e8b7c6d",
        "cart_id": "01JD8Z6Q4M3K2V7R9T5W1XNB0C"
    }
}
```

Store `meta.token` where your storefront keeps credentials, such as an `httpOnly` cookie set by your storefront server, and replace the cart ID you kept with `meta.cart_id`. The `avatar_type` attribute is `null` in this response and `avatar_ui` once the customer is read again, for instance at the next login.

The account gets the customer role set in `roles.user` of `config/shopper/admin.php`, and Shopper fires the `Shopper\Core\Events\Customers\CustomerRegistered` event once the account is saved. Listen to it to send a welcome email or sync the customer to a mailing tool.

An email already in use answers `422 Unprocessable Content` with the `unique` code on the `email` field. The [Errors](/3.x/store-api/errors#validation-errors) page shows the full shape:

```json title="Response 422"
{
    "errors": [
        {
            "status": "422",
            "code": "unique",
            "title": "Unprocessable Content",
            "detail": "The email has already been taken.",
            "source": {
                "pointer": "/data/attributes/email"
            }
        }
    ]
}
```

<Errors>

| Status | Code | When |
|--------|------|------|
| 422 | `unique` | `email` is used by another account |
| 422 | Rule name, such as `required` | Another field fails validation, `password` for a password the `Password::defaults()` rule refuses |

</Errors>

</Endpoint>

### What Happens to the Guest Cart

The `cart_id` sent at registration or login never makes the call fail. The API attaches the cart when it is an open cart that belongs to no customer, or to this customer, and ignores it otherwise: an unknown ID, a completed cart or a cart of another customer.

When the customer already has an open cart, the guest cart is merged into it and `meta.cart_id` is the ID of that existing cart, not the one you sent. When the guest cart cannot be attached, for example because its payment session is already collected, `meta.cart_id` is the guest cart ID. Without `cart_id`, `meta.cart_id` is the latest open cart of the customer, or `null` when there is none. In every case, `meta.cart_id` is the cart your storefront uses from then on.

## Logging In

Login checks an email and a password and issues a new token. Like registration, it takes an optional `cart_id` to bring the guest cart into the customer's account.

<Endpoint id="post-store-auth-login" method="POST" path="/store/auth/login" auth="public" limit="auth">

<Params title="Query parameters">

<Field name="fields[customers]" type="string">
  Comma-separated attributes to return, such as `first_name,last_name`. See [Sparse fieldsets](/3.x/store-api/json-api#sparse-fieldsets).
</Field>

</Params>

<Params title="Body">

<Field name="email" type="string" required>
  The email address of the account.
</Field>

<Field name="password" type="string" required>
  The password of the account.
</Field>

<Field name="cart_id" type="string">
  The ID of a guest cart to attach to the customer, as described in [What Happens to the Guest Cart](#what-happens-to-the-guest-cart).
</Field>

</Params>

This request logs Camille Martin in, and brings her guest cart into her account with `cart_id`:

```bash title="Request"
curl -X POST "http://localhost:8000/store/auth/login" \
  -H "Accept: application/vnd.api+json" \
  -H "Content-Type: application/json" \
  -d '{
    "email": "camille.martin@example.com",
    "password": "sneakers-in-paris",
    "cart_id": "01JD8Z6Q4M3K2V7R9T5W1XNB0C"
  }'
```

The API answers `200 OK` with the same document as registration:

```json title="Response 200"
{
    "data": {
        "id": "01JD9B2K7X4N8R3T6V1Y5Z0QWE",
        "type": "customers",
        "attributes": {
            "first_name": "Camille",
            "last_name": "Martin",
            "email": "camille.martin@example.com",
            "avatar": "https://ui-avatars.com/api/?name=Camille+Martin&color=1d4ed8&background=dbeafe",
            "avatar_type": "avatar_ui",
            "phone_number": null,
            "gender": null,
            "birth_date": null,
            "opt_in": true,
            "email_verified": false,
            "email_verified_at": null,
            "created_at": "2026-11-19T10:24:31+00:00"
        }
    },
    "meta": {
        "token": "4|Pq7Hn2Lw9Xc4Vb8Mz1Rt6Ky3Jd5Sf0Ga2Ue8Wo1N9c1d2e3f",
        "cart_id": "01JD8Z6Q4M3K2V7R9T5W1XNB0C"
    }
}
```

Each login creates a new token and leaves the others valid, so a customer can stay logged in on a phone and a laptop at the same time.

A wrong email or password answers `422 Unprocessable Content` with the `credentials_invalid` code on the `email` field. The message does not say which of the two is wrong. A team member, any user who can open the admin panel (administrators, managers and roles with the `system.dashboard` permission), gets the same answer even with the right password, and the attempt counts as a failed login: the Store API serves customers only, so a team member who also buys on the store needs a separate customer account with another email address.

```json title="Response 422"
{
    "errors": [
        {
            "status": "422",
            "code": "credentials_invalid",
            "title": "Unprocessable Content",
            "detail": "These credentials do not match our records.",
            "source": {
                "pointer": "/data/attributes/email"
            }
        }
    ]
}
```

<Errors>

| Status | Code | When |
|--------|------|------|
| 422 | `credentials_invalid` | The email and the password match no account, or the account belongs to a team member |
| 422 | Rule name, such as `required` | A field fails validation |

</Errors>

</Endpoint>

### Failed Logins

Failed logins are counted per email address and IP address, the key Laravel's own login throttling uses, so an attacker on another network cannot lock a customer out. After 5 failures within a minute (`login_failures` in `config/shopper/http.php`), the API refuses the next attempts for that email from that address, even with the right password, until the minute has passed. A successful login clears the count.

A refused attempt answers `429 Too Many Requests` with the `rate_limited` code and a `Retry-After` header that gives the seconds to wait:

```json title="Response 429"
{
    "errors": [
        {
            "status": "429",
            "code": "rate_limited",
            "title": "Too Many Requests",
            "detail": "Too many login attempts. Please try again in 42 seconds."
        }
    ]
}
```

Show the `detail` to the customer, or a countdown built from `Retry-After`. Shopper fires Laravel's `Illuminate\Auth\Events\Lockout` event on each refused attempt.

## Using the Token

Send the token in the `Authorization` header with the `Bearer` scheme, on every request of the customer, public routes included, so that the API knows who owns the cart:

```bash title="Request"
curl "http://localhost:8000/store/customers/me" \
  -H "Accept: application/vnd.api+json" \
  -H "Authorization: Bearer 4|Pq7Hn2Lw9Xc4Vb8Mz1Rt6Ky3Jd5Sf0Ga2Ue8Wo1N9c1d2e3f"
```

The token carries the `store` ability. The API accepts only tokens that carry it, so a Sanctum token your application issues for another purpose answers `401 Unauthorized` on every Store API route. The tokens of a team member answer the same `401`, so a customer who joins the team can no longer use the tokens issued before.

An expired or revoked token is handled differently by the two route groups:

| Route group | Missing token | Expired or revoked token |
|-------------|---------------|--------------------------|
| Public | Runs as a guest | Runs as a guest: a cart that belongs to the customer answers `404 Not Found` |
| Authenticated | `401 Unauthorized` | `401 Unauthorized` |

The `401` answer carries the `unauthenticated` code:

```json title="Response 401"
{
    "errors": [
        {
            "status": "401",
            "code": "unauthenticated",
            "title": "Unauthorized",
            "detail": "Unauthenticated."
        }
    ]
}
```

On a `401`, or on a `404` for the customer's own cart, drop the stored token and send the customer to the login page. Keep the cart ID: logging in again with `cart_id` attaches the cart back.

## Token Expiration

A token stays valid for 30 days after login or registration. Change the lifetime in minutes with `SHOPPER_API_TOKEN_EXPIRATION`, or set it to `0` to keep tokens until the customer logs out or resets the password. There is no refresh endpoint: when a token expires, the customer logs in again.

```bash title=".env"
SHOPPER_API_TOKEN_EXPIRATION=10080
```

The `expiration` key of `config/sanctum.php` also applies to these tokens when your application sets it, and the shorter of the two lifetimes wins. Expired tokens stay in the `personal_access_tokens` table until the daily `sanctum:prune-expired --hours=24` task deletes them, once the [scheduler runs](/3.x/installation#run-the-scheduler-and-a-queue-worker).

## Logging Out

Logout revokes the token sent with the request and leaves the customer's other tokens valid, so logging out on a phone keeps the laptop session.

<Endpoint id="post-store-auth-logout" method="POST" path="/store/auth/logout" auth="customer">

The route belongs to the authenticated group, so it needs a valid token:

```bash title="Request"
curl -X POST "http://localhost:8000/store/auth/logout" \
  -H "Accept: application/vnd.api+json" \
  -H "Authorization: Bearer 4|Pq7Hn2Lw9Xc4Vb8Mz1Rt6Ky3Jd5Sf0Ga2Ue8Wo1N9c1d2e3f"
```

The API answers `204 No Content`. The customer's cart stays attached to the account and comes back in `meta.cart_id` at the next login.

<Errors>

| Status | Code | When |
|--------|------|------|
| 401 | `unauthenticated` | The token is missing, expired, revoked or not a store token |

</Errors>

</Endpoint>

## Resetting a Password

A password reset takes two calls: the first sends an email with a link to your storefront, the second sends the new password with the token from that link. It uses Laravel's password broker, so the `passwords.users` settings of `config/auth.php` apply: a reset token expires after 60 minutes, and a second email to the same address is not sent within 60 seconds of the first.

<Steps>
<Step title="Point the reset link at your storefront">

The reset email must link to the reset page of your storefront. Set that link before the storefront shows its "Forgot password" form, in the `boot` method of a service provider:

```php title="app/Providers/AppServiceProvider.php"
use Illuminate\Auth\Notifications\ResetPassword;

public function boot(): void
{
    ResetPassword::createUrlUsing(function (object $notifiable, string $token): string {
        return 'https://shop.example.com/reset-password?token='.$token.'&email='.urlencode($notifiable->getEmailForPasswordReset());
    });
}
```

The email is sent by the user model's `Notifiable` trait, through the mail settings of your application.

</Step>
<Step title="Request the email">

<Endpoint id="post-store-auth-forgot-password" method="POST" path="/store/auth/forgot-password" auth="public" limit="auth">

<Params title="Body">

<Field name="email" type="string" required>
  The email address the customer typed in the form.
</Field>

</Params>

Your storefront's "Forgot password" form sends the email address:

```bash title="Request"
curl -X POST "http://localhost:8000/store/auth/forgot-password" \
  -H "Accept: application/vnd.api+json" \
  -H "Content-Type: application/json" \
  -d '{"email": "camille.martin@example.com"}'
```

The API answers `202 Accepted` with an empty body whether or not an account uses that email, so the form cannot reveal who has an account. For the email of a team member, it sends nothing and answers the same `202`: team members reset their password from the admin panel. Show the same message in both cases, such as "If an account exists for this email, a reset link is on its way."

<Errors>

| Status | Code | When |
|--------|------|------|
| 422 | Rule name, such as `email` | `email` is missing or not a valid email address |

</Errors>

</Endpoint>

</Step>
<Step title="Set the new password">

<Endpoint id="post-store-auth-reset-password" method="POST" path="/store/auth/reset-password" auth="public" limit="auth">

<Params title="Body">

<Field name="token" type="string" required>
  The `token` of the reset link.
</Field>

<Field name="email" type="string" required>
  The `email` of the reset link.
</Field>

<Field name="password" type="string" required>
  The new password, checked by the same `Password::defaults()` rule as at registration.
</Field>

</Params>

Your reset page reads `token` and `email` from the link and sends them with the new password. The password follows the same rule as at registration; the API does not ask for a confirmation field, so compare the two inputs in your form.

```bash title="Request"
curl -X POST "http://localhost:8000/store/auth/reset-password" \
  -H "Accept: application/vnd.api+json" \
  -H "Content-Type: application/json" \
  -d '{
    "token": "8f14e45fceea167a5a36dedd4bea2543b1c2d3e4f5a6b7c8d9e0f1a2b3c4d5e6",
    "email": "camille.martin@example.com",
    "password": "new-sneakers-2026"
  }'
```

The API answers `204 No Content`. The reset revokes every token of the customer, so all devices are logged out, and fires Laravel's `Illuminate\Auth\Events\PasswordReset` event. The customer then logs in with the new password.

An expired, used or wrong token answers `422 Unprocessable Content` with the `reset_token_invalid` code on the `email` field. Offer to send a new link:

```json title="Response 422"
{
    "errors": [
        {
            "status": "422",
            "code": "reset_token_invalid",
            "title": "Unprocessable Content",
            "detail": "This password reset token is invalid.",
            "source": {
                "pointer": "/data/attributes/email"
            }
        }
    ]
}
```

<Errors>

| Status | Code | When |
|--------|------|------|
| 422 | `reset_token_invalid` | The token is expired, used or wrong for this email |
| 422 | Rule name, such as `required` | A field fails validation, `password` for a password the `Password::defaults()` rule refuses |

</Errors>

</Endpoint>

</Step>
</Steps>
