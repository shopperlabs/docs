The catalog endpoints feed the pages a visitor browses before the cart: the product grid, the product page, the category menu, the brand and collection pages, the filter sidebar and the reviews. They are read-only and public, so a storefront calls them without a customer token, from the server or from the browser.

Every amount is an integer in cents: a product priced at €90.00 carries `9000`. The [Money](/3.x/money#amounts-in-the-store-api) page covers cents and formatting. Responses are JSON:API documents, and this page lists what each endpoint accepts; the mechanics of `include`, `fields`, `filter`, `sort` and `page` are described once in [JSON:API Conventions](/3.x/store-api/json-api).

## Endpoints

All the catalog routes answer `GET` requests in the public route group. A bearer token is optional: when present, it only changes the prices a custom price resolver returns, as explained in [Prices, currency and stock](#prices-currency-and-stock).

| Method | Path | Purpose |
|--------|------|---------|
| `GET` | `/store/products` | List products, with filters, sorting and price bounds |
| `GET` | `/store/products/{slug}` | Read one product, with its variants and options |
| `GET` | `/store/products/{slug}/reviews` | List the approved reviews of a product, with the rating summary |
| `GET` | `/store/reviews` | Read the latest approved reviews of the shop |
| `GET` | `/store/categories` | List categories |
| `GET` | `/store/categories/tree` | Read the whole category tree in one call |
| `GET` | `/store/categories/{slug}` | Read one category |
| `GET` | `/store/collections` | List collections |
| `GET` | `/store/collections/{slug}` | Read one collection |
| `GET` | `/store/brands` | List brands |
| `GET` | `/store/brands/{slug}` | Read one brand |
| `GET` | `/store/tags` | List product tags |
| `GET` | `/store/attributes` | List the attributes a filter sidebar can offer |

The `{slug}` of a show endpoint is the slug of the record, such as `classic-leather-sneakers`. Its `id` does not work there. The `/store/categories/tree` route is matched before `/store/categories/{slug}`, so a category whose slug is `tree` cannot be read on its own.

## What a Visitor Sees

The API never returns a record the merchant has not made public. Each endpoint applies the same rule as the admin panel, so a storefront does not filter anything itself:

| Resource | Returned when |
|----------|---------------|
| Products | `published_at` is in the past and the product is visible. With a sales channel, the product must also be in that channel. |
| Categories | The category and all its parents are enabled. Disabling a category hides its whole branch. |
| Collections | `published_at` is set and in the past. |
| Brands | The brand is enabled. |
| Tags | Always. |
| Attributes | The attribute is enabled, marked filterable, and of type `checkbox`, `colorpicker` or `select`. |
| Reviews | The review is approved. |

The sales channel comes from the `X-Shopper-Channel` header, or the default channel of the API, as described in [Request headers](/3.x/store-api#request-headers). It filters products only: the product listing, the product page, and the products embedded with `include=products` or counted with `products_count`. Categories, collections, brands, tags and reviews stay the same for every channel. The [Channels](/3.x/channels#what-the-channel-changes) page lists what the channel changes.

A show endpoint answers `404 Not Found` for a record the visitor cannot see, exactly as for a slug that does not exist:

```json title="Response"
{
    "errors": [
        {
            "status": "404",
            "code": "not_found",
            "title": "Not Found",
            "detail": "Not Found"
        }
    ]
}
```

## Listing Products

The product listing powers the shop page, the category pages, the search results and the brand pages: the same endpoint with different filters. The simplest call returns the first 15 published products, in the order they were created:

```bash title="Request"
curl http://localhost:8000/store/products \
  -H "Accept: application/vnd.api+json" \
  -H "X-Shopper-Zone: EU"
```

A category page filters by the category slug and picks a page size. The `-g` option stops curl from reading the brackets of the query string:

```bash title="Request"
curl -g "http://localhost:8000/store/products?filter[category]=men-shoes&page[size]=2" \
  -H "Accept: application/vnd.api+json" \
  -H "X-Shopper-Zone: EU"
```

### The Product Resource

Some attributes depend on the product type or on an include. An attribute that does not apply is left out of the response, not sent as `null`:

| Attribute | Description |
|-----------|-------------|
| `name`, `slug` | Name, and the slug the product page reads with `/store/products/{slug}`. |
| `sku`, `barcode` | Codes of the product. A variant product keeps its codes on each variant. |
| `summary`, `description` | Short and long description, as entered in the admin panel. |
| `featured` | `true` for a product the merchant highlights. |
| `type` | `standard`, `variant`, `virtual` or `external`. See [Products](/3.x/products). |
| `published_at` | Publication date, in ISO 8601. |
| `seo_title`, `seo_description` | Values for the page `<title>` and meta description. |
| `metadata` | Your own data, or `null`. |
| `external_id` | External products only: the ID on the platform that sells the product. |
| `stock`, `in_stock` | Availability. See [Stock](#stock). |
| `price_range` | Lowest and highest price in the currency of the request. See [Prices, currency and stock](#prices-currency-and-stock). |
| `prices` | Every price of the product in an enabled currency. Empty for a variant product. |
| `calculated_price`, `quantity_rule` | The price to charge in the currency of the request, and the quantity limits. Not on variant products. |
| `images` | Every image of the gallery, as media objects. |
| `thumbnail` | The thumbnail image, or the first gallery image when the product has no thumbnail, or `null`. |
| `files` | Virtual products only: the downloadable files, each with `id`, `name`, `extension` and `size` in bytes. The files themselves are downloaded from the order, see [Orders](/3.x/store-api/orders). |
| `rating`, `reviews_count` | With `include=rating` only: the average rating of the approved reviews, rounded to one decimal or `null` without reviews, and their number. |
| `options` | With `include=options` only. See [Options](#options). |
| `created_at`, `updated_at` | Dates in ISO 8601. |

A media object carries the `id` of the file, its `url`, the `conversions` already generated (by default `large` at 800 x 800 and `medium` at 500 x 500, keyed by name), the file `name` and `extension`, and its dates. A conversion that is not generated yet is missing from `conversions`, so fall back to `url`.

The product relationships are `brand`, `categories`, `collections`, `tags`, `relatedProducts`, and `variants` on variant products. A relationship appears in `relationships` only when it is requested with `include`.

### Filters, Sorting and Includes

The listing accepts the filters, sorts and includes of `resources.product` in `config/shopper/api.php`. A comma inside one filter means OR, such as `filter[brand]=maison-cuir,nordic-steps`, and different filters combine with AND. A filter accepts up to 50 values; more returns `422` with the code `filter_too_wide`. An unknown filter, sort or include returns `400` with the code `bad_request`. The [Errors](/3.x/store-api/errors#error-codes) page lists every code.

<ApiTable name="GET /store/products" label="Parameter">

<ParamField path="filter[q]" type="string">
  Search term, matched case-insensitively anywhere in the name, the description or the SKU of the product. Only the first comma-separated term is searched, and `%` and `_` act as wildcards.
</ParamField>

<ParamField path="filter[name]" type="string">
  Keeps the products whose name contains the value, case-insensitively.
</ParamField>

<ParamField path="filter[sku]" type="string">
  Exact SKU of the product. The SKUs of variants are not searched.
</ParamField>

<ParamField path="filter[featured]" type="boolean">
  `true` keeps the featured products, `false` the others.
</ParamField>

<ParamField path="filter[in_stock]" type="boolean">
  `true` keeps what a visitor can buy now: external products, products with stock left or that allow backorders, and variant products with at least one such variant. `false` keeps the rest.
</ParamField>

<ParamField path="filter[category]" type="string">
  Slug or ID of a category. Keeps the products assigned to that category itself, without its subcategories. A hidden category matches nothing.
</ParamField>

<ParamField path="filter[category_tree]" type="string">
  Slug or ID of a category. Keeps the products of that category and of every enabled category below it. Use it for a parent category page such as "Men".
</ParamField>

<ParamField path="filter[collection]" type="string">
  Slug or ID of a published collection.
</ParamField>

<ParamField path="filter[brand]" type="string">
  Slug or ID of an enabled brand.
</ParamField>

<ParamField path="filter[tag]" type="string">
  Slug or ID of a tag.
</ParamField>

<ParamField path="filter[option]" type="string">
  Key or label of an attribute value, such as `42` or `Black`. Keeps the products with a variant that carries the value, or with the value set on the product, whatever the attribute. See [Attributes](#attributes).
</ParamField>

<ParamField path="filter[currency]" type="string">
  ISO code of an enabled currency, such as `USD`, in any case. Sets the currency of every price, price sort and price bound of the response. Defaults to the currency of the zone, then to the default currency of the shop.
</ParamField>

<ParamField path="filter[price_min]" type="integer">
  Lowest price to keep, in cents, in the currency of the request. Products without a price in that currency are left out.
</ParamField>

<ParamField path="filter[price_max]" type="integer">
  Highest price to keep, in cents, in the currency of the request. Products without a price in that currency are left out.
</ParamField>

<ParamField path="sort" type="string">
  `name`, `created_at`, `published_at` or `price`, prefixed with `-` for descending order, such as `-published_at` for the newest first. Without `sort`, products come in creation order. See [Sorting](/3.x/store-api/json-api#sorting).
</ParamField>

<ParamField path="include" type="string">
  Comma-separated list from the includes table below. See [Includes](/3.x/store-api/json-api#includes).
</ParamField>

<ParamField path="fields[products]" type="string">
  Comma-separated attributes to return, such as `name,slug,price_range,thumbnail`. See [Sparse fieldsets](/3.x/store-api/json-api#sparse-fieldsets).
</ParamField>

<ParamField path="page[size]" type="integer" default="15">
  Products per page, from 1 to 100.
</ParamField>

<ParamField path="page[number]" type="integer" default="1">
  Page to return, from 1 to 100. Past page 100, switch to `page[cursor]`. See [Pagination](/3.x/store-api/json-api#pagination).
</ParamField>

<ParamField path="page[cursor]" type="string">
  Cursor from the `links` of a previous page. Switches the listing to cursor pagination.
</ParamField>

</ApiTable>

The includes add related records, or extra attributes computed on demand:

| Include | Adds |
|---------|------|
| `brand` | The brand, when it is enabled. |
| `categories` | The categories of the product that sit in a visible branch, with their parent loaded. |
| `collections` | The published collections of the product. |
| `tags` | The tags of the product. |
| `variants` | The variants of a variant product, with their prices, stock and option values. |
| `options` | The `options` attribute: the attributes and values the product uses. |
| `relatedProducts` | The related products that are published and in the sales channel, with their stock and `price_range`. |
| `rating` | The `rating` and `reviews_count` attributes, from the approved reviews. |
| `price_range` | Listing only: `meta.price_range`, the lowest and highest price of the products that match the filters. See [Price filters and sorting](#price-filters-and-sorting). |

Several filters together build a search results page with facets. This request searches "leather" in the products of the "Men" branch that are in stock, from the brand Maison Cuir, newest first:

```bash title="Request"
curl -g "http://localhost:8000/store/products?filter[q]=leather&filter[category_tree]=men&filter[in_stock]=true&filter[brand]=maison-cuir&sort=-published_at&include=brand,rating" \
  -H "Accept: application/vnd.api+json" \
  -H "X-Shopper-Zone: EU"
```

## Prices, Currency and Stock

A storefront shows prices in one currency per page, and the API resolves that currency once per request so every amount of the response agrees. Prices are never converted: an amount always comes from a price the merchant set in that currency, and a product without a price in the currency shows no amount at all.

The currency of a request is, in this order:

1. The `filter[currency]` query parameter, on the listing and on the product page.
2. The currency of the zone sent in `X-Shopper-Zone`, or of the default zone. See [Picking a zone and a currency](/3.x/store-api/store).
3. The default currency of the shop.

A code in `filter[currency]` that matches no enabled currency is an error, never a silent fallback. The API answers `422 Unprocessable Content`:

```json title="Response"
{
    "errors": [
        {
            "status": "422",
            "code": "currency_unknown",
            "title": "Unprocessable Content",
            "detail": "The \"EURO\" currency is unknown or not enabled on this shop.",
            "source": {
                "pointer": "/data/attributes/filter/currency"
            }
        }
    ]
}
```

The check runs against every enabled currency, not only the currencies the shop sells in, and Shopper enables all 158 currencies at install. A code such as `GBP` on a shop that sells in EUR and USD passes with `200 OK`, and every `calculated_price` and `price_range` of the response is `null`. Send a code from the `currencies` of the [store settings](/3.x/store-api/store#reading-the-store-settings), the list a cart accepts.

A product carries up to four price attributes. Read the one that matches what the page shows:

| Attribute | Shape | Use it for |
|-----------|-------|------------|
| `calculated_price` | `amount`, `compare_amount`, `original_amount`, `currency_code`, `meta` | The price to display and charge for a standard, virtual or external product, and for each variant on the product page. `null` when there is no price in the currency. |
| `quantity_rule` | `minimum`, `maximum`, `increment` | The quantity limits of the quantity picker. `null` when no rule applies. |
| `price_range` | `currency_code`, `min`, `max` | "From" prices on cards, mostly for variant products: the lowest and highest price of the product or of its variants. `null` when there is no price in the currency. |
| `prices` | A list of `public_id`, `amount`, `compare_amount`, `currency_code` | Every price of the product in every enabled currency, as the merchant set them. Empty for a variant product. |

`compare_amount` is the "compare at" price to strike through, or `null`. With the default price resolver, `calculated_price.amount` is the price set for the currency, `original_amount` and `meta` are `null`, and `quantity_rule` is `null`. A custom resolver can return a customer price instead: the API passes it the currency, the zone, the channel and the customer of the bearer token, if any. Product responses carry `Vary: Authorization` for that reason, so a shared cache must not serve one customer's prices to another. The [Pricing](/3.x/pricing#custom-price-resolver) page covers resolvers and [quantity rules](/3.x/pricing#quantity-rules).

To show the prices of a product in US dollars whatever the zone, pass the currency:

```bash title="Request"
curl -g "http://localhost:8000/store/products/leather-care-kit?filter[currency]=USD&fields[products]=name,price_range,prices,calculated_price" \
  -H "Accept: application/vnd.api+json" \
  -H "X-Shopper-Zone: EU"
```

The API answers `200 OK`. `price_range`, `calculated_price` and `meta.currency` follow the requested currency, while `prices` still lists every currency:

```json title="Response"

        "id": "01JD8YQ2B3C4D5E6F7G8H9JKM0",
        "type": "products",
        "attributes": {
            "name": "Leather Care Kit",
            "price_range": {
                "currency_code": "USD",
                "min": 2190,
                "max": 2190
            },
            "prices": [
                {
                    "public_id": "01JD8YQ7P9R1T3V5X7Z9B1D3F5",
                    "amount": 1990,

                    "currency_code": "EUR"

                {
                    "public_id": "01JD8YQ7P9R1T3V5X7Z9B1D3F6",
```

### Price Filters and Sorting

A price slider needs two things: the products within the chosen bounds, and the bounds of the slider itself. `filter[price_min]`, `filter[price_max]` and `sort=price` work on the lowest price of each product in the currency of the request: the price of a standard product, or the cheapest variant of a variant product. Products without a price in that currency are left out of the results. Bounds are integers in cents.

`include=price_range` adds `meta.price_range`, the lowest and highest of these prices over every product that matches the other filters. It ignores `price_min` and `price_max`, so the slider keeps its full range while the visitor moves it. This request keeps the products of the "Men" branch between €50.00 and €100.00, cheapest first, and asks for the slider range:

```bash title="Request"
curl -g "http://localhost:8000/store/products?filter[category_tree]=men&filter[price_min]=5000&filter[price_max]=10000&sort=price&include=price_range&fields[products]=name,price_range" \
  -H "Accept: application/vnd.api+json" \
  -H "X-Shopper-Zone: EU"
```

The API answers `200 OK`. One product falls within the bounds, and `meta.price_range` covers the whole branch, from the €19.90 care kit to a €189.00 jacket:

### Stock

A product card needs to know whether to show "Add to cart" or "Sold out", and the API computes that per product type, so the storefront reads one boolean:

| Product type | Attributes |
|--------------|------------|
| `standard`, `virtual` | `stock`, the quantity on hand, and `in_stock`: `true` when `stock` is above 0 or the product allows backorders. |
| `variant` | `in_stock` only: `true` when at least one variant has stock or allows backorders. Each variant carries its own `stock` and `in_stock` with `include=variants`. |
| `external` | `in_stock`, always `true`. The product is sold elsewhere. |

The listing, the product page, related products, and the products embedded in brands and categories carry these attributes. The products embedded with `include=products` in collections and tags do not, so read the stock from the product listing with `filter[collection]` or `filter[tag]` instead. The [Product variants](/3.x/product-variants#stock-management) page covers how stock is counted.

## Categories

Categories give the storefront its menu, its category pages and its breadcrumbs. The API offers three reads: the tree for the menu, the listing for flat lists such as a sitemap, and the category itself for a category page.

### The Category Tree


## Tags

Tags label products across categories, such as "vegan" or "new-season". The API lists every tag, with no show endpoint, so a storefront uses them to build filter chips or tag pages:

```bash title="Request"
curl -g "http://localhost:8000/store/tags?sort=name&page[size]=50" \
  -H "Accept: application/vnd.api+json"
```

Each tag carries `name`, `slug`, `created_at` and `updated_at`. The listing accepts `filter[name]` (partial match), `sort=name`, `include=products` and the pagination parameters. As with collections, the products embedded in a tag carry no stock, so a tag page calls the product listing with `filter[tag]=vegan`.

```json title="Response"
        "rating_distribution": {
            "1": 0,
            "2": 0,
            "3": 1,
            "4": 3,
            "5": 8
        }
    }
}
```

`average_rating` is rounded to one decimal, and `null` when the product has no approved review. `rating_distribution` always has the five keys, so a storefront draws the bars without checking for missing ratings. `author` is `null` when the author account no longer exists. The endpoint accepts `filter[rating]` (exact), `sort=created_at` or `sort=rating` with `-` for descending (the default is `-created_at`), and the pagination parameters.

For the stars on a product card, `include=rating` on the product listing is cheaper: it adds `rating` and `reviews_count` to each product without reading the reviews.

### Latest Reviews

A home page testimonials block shows the most recent reviews of the whole shop. `/store/reviews` returns the latest approved reviews, newest first, capped at 20 by `resources.review.latest_limit` in `config/shopper/api.php`:

```bash title="Request"
curl http://localhost:8000/store/reviews \
  -H "Accept: application/vnd.api+json"
```

The response holds a `data` list of reviews in the shape above, with no `links` or `meta`: the endpoint has no pagination, filters or sorting. A review does not say which product it belongs to, so this block cannot link a review to its product page.
