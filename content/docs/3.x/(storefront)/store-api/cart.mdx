A storefront keeps the shopping basket of a visitor in a Shopper cart. The Store API creates the cart, prices every line from the catalog, checks stock, applies promotion codes, computes tax once a shipping address is known, and returns the totals with every response. The storefront never computes a price: it sends what the customer picked and renders the cart the API answers with.

Every amount in a cart response is an integer in cents: a line priced at €90.00 carries `9000`. The [Money](/3.x/money) page covers cents and formatting. The [Checkout](/3.x/store-api/checkout) guide picks up where this page ends, with shipping, payment and the order.

## Endpoints

The cart endpoints sit in the public route group: they work without a customer token, and with one. The ones that create or add things share the checkout rate limit of 30 requests per minute (`shopper.http.rate_limiters`), on top of the general limit described in [Rate limits](/3.x/store-api#rate-limits). On these public routes both limits count requests per IP address, for guests and logged-in customers alike.

Request bodies are flat JSON objects, such as `{"quantity": 2}`, sent with `Content-Type: application/json`. Responses are JSON:API documents, described in [JSON:API Conventions](/3.x/store-api/json-api). Every endpoint of this page answers with the whole cart, so the storefront re-renders from the response without a second call.

## Creating a Cart

A storefront creates the cart the first time the visitor adds something, and keeps its ID for every later call. The cart takes its zone from the `X-Shopper-Zone` header of this request, or the default zone when the header is missing, as described in [Request headers](/3.x/store-api#request-headers). The zone sets the prices, the shipping options and the payment methods the cart offers.

<Endpoint id="post-store-carts" method="POST" path="/store/carts" auth="optional" limit="checkout">

<Params title="Query parameters">

<Field name="include" type="string">
  Related resources to return with the cart, listed in [Reading a Cart](#reading-a-cart).
</Field>

<Field name="fields[carts]" type="string">
  Comma-separated attributes to return, such as `lines_count,total`. See [Sparse fieldsets](/3.x/store-api/json-api#sparse-fieldsets).
</Field>

</Params>

<Params title="Body">

<Field name="currency_code" type="string">
  ISO code of an enabled currency of the shop, such as `EUR`. Upper-cased before validation. Defaults to the currency of the zone, then to the default currency of the shop.
</Field>

<Field name="email" type="string">
  Contact email of the checkout, lower-cased. Up to 255 characters.
</Field>

<Field name="metadata" type="object">
  Your own data, such as a gift note or a tracking source. Up to 50 keys and 4,096 characters once encoded as JSON.
</Field>

</Params>

Every parameter is optional, so an empty body creates a cart in the currency of the zone:

```bash title="Request"
curl -X POST http://localhost:8000/store/carts \
  -H "Accept: application/vnd.api+json" \
  -H "Content-Type: application/json" \
  -H "X-Shopper-Zone: EU" \
  -d '{"email": "camille.martin@example.com"}'
```

The API answers `201 Created` with the new cart. Its `id` is the cart ID the storefront stores:

```json title="Response 201"
{
    "data": {
        "id": "01JD8Z6Q4M3K2V7R9T5W1XNB0C",
        "type": "carts",
        "attributes": {
            "currency_code": "EUR",
            "email": "camille.martin@example.com",
            "promotions": [],
            "completed_at": null,
            "metadata": null,
            "lines_count": 0,
            "lines_quantity": 0,
            "subtotal": 0,
            "discount_total": 0,
            "tax_total": 0,
            "shipping_total": 0,
            "total": 0,
            "tax_inclusive": false,
            "shipping_option_id": null,
            "created_at": "2026-11-19T10:15:00+00:00",
            "updated_at": "2026-11-19T10:15:00+00:00"
        }
    }
}
```

A `currency_code` that is unknown, disabled or not one of the shop currencies answers `422` with the code `exists` on `/data/attributes/currency_code`.

| Status | Code | When |
|--------|------|------|
| 422 | `exists` | `currency_code` is unknown, disabled or not one of the shop currencies |

</Errors>

</Endpoint>

## Guest and Customer Carts

Who can use a cart depends on the request that created it. A request without a customer token creates a guest cart. A request with the bearer token of a logged-in customer, described in [Logging in](/3.x/store-api/authentication#logging-in), creates a cart that belongs to that customer. Send the same token on every later call for that cart.

A guest cart has no owner: any request that carries its ID can read and change it. The ID is a ULID, 26 characters with 80 random bits, so it cannot be guessed, but it works like a session token. Keep it where the visitor's session lives, such as an `HttpOnly` cookie or the secure storage of a mobile app, and keep it out of URLs, logs and analytics events.

A customer cart answers only to its owner. A request without the token, or with the token of another customer, gets `404 not_found`, the same answer as an ID that does not exist, so the API never confirms that a cart exists. An expired or revoked token counts as no token, so the customer cart also answers `404` once the token expires: log the customer in again before creating a new cart. A valid token without the `store` ability answers `401 unauthenticated`, even on these public routes.

When a guest logs in during checkout, transfer the guest cart to the customer with the cart transfer endpoint described in [Customers](/3.x/store-api/customers). The cart then answers only to that customer.

A completed cart, one that became an order, stays readable with the same ID. Any change to it answers `409 cart_completed`. Open carts that see no activity for 30 days are deleted by the scheduled `shopper:prune-carts` command, as the [Cart](/3.x/cart) page describes, so a storefront that gets `404` on a stored ID creates a new cart.

## Adding a Line

A line is one product or one variant in the cart, with its quantity. The storefront sends the type and the public ID of what the customer picked; the API finds it in the catalog, prices it in the cart currency and checks stock. The client never sends a price.

### Products and Variants

A product that has variants is sold through them. Adding such a product with `purchasable_type: "product"` answers `422 variant_required` on `/data/attributes/purchasable_id`: the storefront asks the customer for a size or a color and adds the variant. The [Catalog](/3.x/store-api/catalog) guide shows how to read the variants of a product, and [Product Variants](/3.x/product-variants) explains how they are built.

The API accepts a product when it is published and not an external product, and a variant when its product is published. Anything else answers `422 purchasable_unavailable` on `/data/attributes/purchasable_id`. A purchasable that has prices, but none in the cart currency, answers `422 price_missing` on `/data/attributes/purchasable_id`.

### Stock and Quantity Rules

The API checks stock when a line is added or its quantity changes. A variant or product that tracks its inventory and does not allow backorders answers `422 stock_insufficient` on `/data/attributes/quantity` when the stock cannot cover the quantity. The check runs again when the order is placed, as the [Checkout](/3.x/store-api/checkout) guide explains.

A price can carry quantity rules (a minimum, a maximum, an increment), described in [Pricing](/3.x/pricing). A quantity that breaks one answers `422 quantity_rule_violated` with a `meta` object, so the storefront can correct the quantity selector:

```json title="Response 422"
{
    "errors": [
        {
            "status": "422",
            "code": "quantity_rule_violated",
            "title": "Unprocessable Content",
            "detail": "This item must be ordered in multiples of 2.",
            "source": { "pointer": "/data/attributes/quantity" },
            "meta": {
                "purchasable_id": "01JD8YQ3H5K7M9P2R4T6V8X0Z1",
                "quantity": 3,
                "minimum": 2,
                "maximum": null,
                "increment": 2
            }
        }
    ]
}
```

## Reading a Cart

A storefront reads the cart to render the basket page or the mini cart. The totals come with the cart, so one request is enough: the API reuses the stored totals when they were calculated in the last 15 minutes (`shopper.cart.totals_ttl_minutes`) and recalculates them otherwise.

<Endpoint id="get-store-carts-cartid" method="GET" path="/store/carts/{cartId}" auth="owner">

<Params title="Path parameters">

<Field name="cartId" type="string" required>
  The cart ID, the `id` returned by [Creating a Cart](#creating-a-cart).
</Field>

</Params>

<Params title="Query parameters">

<Field name="include" type="string">
  Related resources to return with the cart, comma-separated, from the table below.
</Field>

<Field name="fields[carts]" type="string">
  Comma-separated attributes to return, such as `lines_count,total`. See [Sparse fieldsets](/3.x/store-api/json-api#sparse-fieldsets).
</Field>

</Params>

The cart document carries only the cart attributes by default. The `include` query parameter adds related resources, as described in [Includes](/3.x/store-api/json-api#includes). The cart accepts these paths, which `CartResource` declares in its `includes()` method:

| Include | Adds |
|---------|------|
| `lines` | The cart lines |
| `lines.purchasable` | The lines and the variant or product of each line |
| `lines.purchasable.product` | The same, plus the parent product of each variant |
| `addresses` | The shipping and billing addresses |
| `paymentMethod` | The payment method chosen at checkout |

Any other path answers `400 bad_request`. A basket page asks for `lines.purchasable` to show the variant of each line, or `lines.purchasable.product` to add the parent product and its images:

```bash title="Request"
curl "http://localhost:8000/store/carts/01JD8Z6Q4M3K2V7R9T5W1XNB0C?include=lines.purchasable" \
  -H "Accept: application/vnd.api+json"
```

The API answers `200 OK`. In this trimmed response, the cart keeps its totals and the variant keeps three of its attributes; the [Catalog](/3.x/store-api/catalog) guide lists them all:

The quantity selector of the basket page changes a line through its ID, the `id` of the `cart-lines` resource. A quantity of zero is not accepted: removing a line has its own endpoint.

This request brings the line of sneakers from two pairs down to one:


## Promotion Codes

A promotion code entered by the customer is checked against the whole cart before it is kept: its currency, zone, dates, eligible products, minimum amount or quantity, usage limits and campaign budget. A code that cannot apply is refused and leaves the cart as it was. Automatic promotions need no request: they appear in `promotions` as soon as the cart qualifies. The [Discounts](/3.x/discounts) page describes how promotions are set up.

This request applies the code `WELCOME10` to the cart:

```bash title="Request"
curl -X POST http://localhost:8000/store/carts/01JD8Z6Q4M3K2V7R9T5W1XNB0C/promotion \
  -H "Accept: application/vnd.api+json" \
  -H "Content-Type: application/json" \
  -d '{"code": "WELCOME10"}'
```

The API answers `200 OK` with the cart. `WELCOME10` takes 10% off the subtotal, and the VAT is recalculated on the discounted amount. The response is trimmed to the totals:

```json title="Response 200"
{
    "data": {
        "id": "01JD8Z6Q4M3K2V7R9T5W1XNB0C",
        "type": "carts",
        "attributes": {
            "currency_code": "EUR",
            "promotions": [
                {
                    "code": "WELCOME10",
                    "source": "code",
                    "amount": 1800,
                    "status": "applied"
                }
            ],
            "subtotal": 18000,
            "discount_total": 1800,
            "tax_total": 2700,
            "shipping_total": 0,
            "total": 16200,
            "tax_inclusive": true
        }
    }
}
```

Each entry of `promotions` has a `source` of `code` or `automatic`, the `amount` it takes off the cart in cents, and a `status`. A promotion is `applied` when its amount is above zero, and `suppressed` when it takes nothing off the cart right now, such as a code that an exclusive promotion of higher priority overrides. A suppressed code stays on the cart. A cart applies at most 5 promotions at once (`shopper.cart.max_promotions`). Each line shows its share of the discount in its own `adjustments`, with the code and the amount.

A code the cart cannot use answers `422 promotion_not_applicable`, with the same message whatever the reason, so codes cannot be discovered by trying them:

```json title="Response 422"
{
    "errors": [
        {
            "status": "422",
            "code": "promotion_not_applicable",
            "title": "Unprocessable Content",
            "detail": "This promotion code does not apply to your cart.",
            "source": { "pointer": "/data/attributes/code" }
        }
    ]
}
```

## Updating the Cart

The cart itself has four fields a storefront changes after creating it: the currency of a currency switcher, the zone of a country picker, the email of the checkout form and the metadata. Send only the fields that change.

<Endpoint id="patch-store-carts-cartid" method="PATCH" path="/store/carts/{cartId}" auth="owner">

<Params title="Path parameters">

<Field name="cartId" type="string" required>
  The cart ID.
</Field>

</Params>

<Params title="Query parameters">

<Field name="include" type="string">
  Related resources to return with the cart, listed in [Reading a Cart](#reading-a-cart).
</Field>

<Field name="fields[carts]" type="string">
  Comma-separated attributes to return, such as `lines_count,total`. See [Sparse fieldsets](/3.x/store-api/json-api#sparse-fieldsets).
</Field>

</Params>

<Params title="Body">

<Field name="currency_code" type="string">
  ISO code of an enabled currency of the shop. The lines are priced again in that currency.
</Field>

<Field name="zone_code" type="string">
  Code of an enabled zone, the code the `X-Shopper-Zone` header carries. The lines are priced again for that zone.
</Field>

<Field name="email" type="string">
  Contact email of the checkout, lower-cased.
</Field>

<Field name="metadata" type="object">
  Replaces the cart metadata. `null` clears it.
</Field>

</Params>

This request switches the cart to US dollars:

```bash title="Request"
curl -X PATCH http://localhost:8000/store/carts/01JD8Z6Q4M3K2V7R9T5W1XNB0C \
  -H "Accept: application/vnd.api+json" \
  -H "Content-Type: application/json" \
  -d '{"currency_code": "USD"}'
```

The API answers `200 OK` with the cart priced in the new currency. Switching currency or zone resets part of the checkout:

| Change | Lines | Shipping method | Payment method | Promotion codes |
|--------|-------|-----------------|----------------|-----------------|
| `currency_code` | Priced again in the new currency | Removed | Kept | Dropped when they no longer apply |
| `zone_code` | Priced again for the new zone | Removed | Removed | Dropped when they no longer apply |

The currency of the cart stays the same on a zone switch: send both fields to change both. When a line has no price in the new currency, the API refuses with `422 price_missing` on `/data/attributes/currency_code` and changes nothing. A line with a custom price cannot change currency and answers `409 cart_line_locked`.

## Errors

Errors use the JSON:API error object, with a `code` a client can branch on, described with every code in [Error codes](/3.x/store-api/errors#error-codes). On top of validation errors, `401 unauthenticated` for a rejected token and `429 rate_limited`, the cart endpoints answer with these codes:

| Code | Status | Endpoints | When |
|------|--------|-----------|------|
| `not_found` | 404 | All but `POST /carts` | No cart with this ID for this request, or no line with this ID in the cart |
| `bad_request` | 400 | All that answer with the cart | An `include` path outside the cart allowlist |
| `purchasable_unavailable` | 422 | Add a line | The product or variant cannot be bought |
| `variant_required` | 422 | Add a line | The product is sold through its variants |
| `price_missing` | 422 | Add a line, update the cart | No price in the cart currency, or in the new currency |
| `stock_insufficient` | 422 | Add a line, update a line | Not enough stock for the quantity |
| `quantity_rule_violated` | 422 | Add a line, update a line | The quantity breaks a minimum, maximum or increment, details in `meta` |
| `cart_line_metadata_conflict` | 422 | Add a line | The line already exists with other metadata |
| `promotion_not_applicable` | 422 | Apply a code | The code does not exist or does not apply to the cart |
| `cart_line_locked` | 409 | Update a line, update the cart | The line has a custom price |
| `cart_completed` | 409 | All changes | The cart is already an order |
| `payment_session_collected` | 409 | All changes | The customer already paid: the cart can no longer change, complete it |
| `payment_session_in_progress` | 409 | All changes | Another request is changing the cart, retry after the `Retry-After` header (3 seconds) |
| `payment_provider_unavailable` | 503 | All changes | The open payment could not be cancelled at the provider, retry after the `Retry-After` header (5 seconds) |

The last three come from the payment session a checkout opens. A change to the cart that alters its total cancels that session, and the storefront opens a new one, as the [Checkout](/3.x/store-api/checkout) guide explains.
